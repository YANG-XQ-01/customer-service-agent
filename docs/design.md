# 电商智能客服 Agent · 总体设计方案（阶段 0）

## 0. 文档目的

本文件记录阶段 0 已确认的设计，作为后续 7 个阶段的施工图和教学索引。
随着阶段推进，相关章节会补充具体细节（如状态字段最终形态、数据表结构）。

## 1. 项目定位

做一个能跑在网页上的电商客服：用户发一句自然语言，
系统判断意图（查订单 / 售后 / 商品与政策咨询 / 闲聊），
调对应工具或检索知识库，用大模型组织回答；搞不定就转人工。

对求职而言，它的价值点在于覆盖一条完整的工程链：
FastAPI 接口 → 单 Agent 工具调用 → LangGraph 多智能体编排 →
转人工策略 → 评测与优化 → 容器化部署。

## 2. 已确认的关键选型

| 决定 | 结论 | 为什么 / 替代方案 |
|---|---|---|
| 大模型 | 通义千问 qwen-plus（阿里云百炼 OpenAI 兼容接口） | 与已有 RAG 项目一致，密钥已有；兼容 OpenAI 格式，以后可换模型而不改代码。替代：OpenAI GPT（国内访问、成本不如千问）。 |
| 知识库 | Milvus | 已有 Milvus + Docker 使用经验，向量库服务化，适合“知识文档检索”的生产形态。替代：FAISS/Chroma（轻量但非服务化）。 |
| 业务数据 | MySQL 8 | 订单/售后单是结构化事实，适合 SQL 精确查询。替代：本地 JSON mock（更简单，但面试深度弱）。 |
| 前端 | 原生 HTML/CSS/JS 聊天页 | 零前端依赖，求职演示直观；已有同类页面经验可复用。 |
| 编排 | 阶段 2 先单 Agent → 阶段 3 起 LangGraph 多智能体 | 先用高层 Agent 建立“工具调用”直觉并作对照组，再升级为显式可控的流程图。替代：全程高层 Agent（代码少，但业务流程难控制、面试讲不深）。 |

## 3. 数据边界：MySQL 与 Milvus 各管什么

- **结构化事实（订单号、状态、金额、售后单）→ MySQL**：SQL 精确查询，结果可信、可解释。
- **非结构化知识（商品介绍、退换货政策、物流说明）→ Milvus**：文本向量化后做语义检索，再交给大模型基于资料回答（RAG）。

两者不可互换：让模型“查”订单状态必须走工具拿精确数据，否则会编造；
而政策类问题没有“唯一答案”，需要靠向量检索召回相关资料再生成。
两个都接入后，Agent 才能学会“查订单调工具、问政策去检索”。

## 4. 单 Agent 版流程（阶段 2 目标，先建立直觉）

```text
用户消息
   │
高层 Agent（大模型 + 一份工具清单）
   │  自己判断该调哪个工具
   ├─→ get_order_status(查订单)
   ├─→ get_logistics(查物流)
   ├─→ 知识库检索(商品/政策)
   └─→ 拿到结果 → 组织自然语言回答
```

特点：代码量少、模型自主选工具、内部像黑盒。
好处：快速理解“工具调用”；坏处：业务规则（如退款超阈值转人工）很难塞进去。
这段体验正好是阶段 3 的对照组。

## 5. 多智能体版架构（阶段 3+ 目标）

```text
用户消息
   │
入口节点（加载会话历史）
   │
路由节点（LLM 判断意图，条件边分派）
   ├─→ 订单 Agent    → 提取订单号 → get_order_status / get_logistics
   ├─→ 售后 Agent    → 查询售后单 + 政策检索 + 金额/类型校验
   ├─→ 知识 Agent    → Milvus 检索 → 基于资料回答
   ├─→ 闲聊/通用节点  → 直接回复
   └─→ 转人工节点    → 打包 handoff_context（兜底）
   │
输出节点（最终回答）
```

要点：

- **节点**：入口、路由、各专家 Agent、转人工、输出。
- **边**：普通边 + 条件边（按意图走分支、按失败次数判断是否转人工、按步数上限防死循环）。
- **状态（集中数据包）**：
  - `messages`：完整对话历史；
  - `intent`：路由判断出的意图；
  - `slots`：从对话里抽出的关键信息（订单号、商品名等）；
  - `tool_results`：最近一次工具返回；
  - `retrieved_docs`：知识检索命中的片段；
  - `tool_logs`：每一步工具调用日志（名称、参数、返回、耗时）；
  - `attempts`：当前会话连续失败/无法回答次数；
  - `handoff_context`：转人工时要带走的上下文。

### 为什么用路由节点而不是提示词硬分

“一个大 Agent + 全部工具 + 一条很长的提示词”也能做，但有三个问题：

1. **维护性差**：意图一多，提示词之间互相打架，改一处影响全局；
2. **规则难加**：退款金额校验、连续失败转人工这类硬规则，提示词里只能“求”模型遵守；
3. **不可观测**：黑盒里发生了什么很难复盘。

路由节点把“选谁干活”变成流程图里看得见的一步，
每个分支还能附加自己的校验逻辑，日志也能精确到节点级别。

## 6. MySQL 数据模型（初稿，阶段 2 定稿）

```text
orders        订单表：order_no、user_id、status、total_amount、created_at…
after_sales   售后单表：order_no、user_id、type(退货/退款)、status、refund_amount、reason…
users         用户表：user_id、name…
```

配套一个演示数据种子脚本，造几个固定用户和订单方便现场演示。
正式表结构在阶段 2 实现时按实际查询需求微调。

## 7. Milvus 知识库（初稿）

- Collection：`customer_service_kb`，字段含 `text / metadata / vector`。
- 知识来源：`data/knowledge/` 下的商品说明、退换货政策、物流政策等文档（10+ 篇），阶段 2 提供入库脚本。
- 实现参照已有 ops-knowledge-base 项目的 LangChain 1.x + langchain-milvus 写法。

## 9. 阶段路线、验证方式与通过条件

| 阶段 | 做什么 | 交付物 | 怎么验证 | 通过条件 |
|---|---|---|---|---|
| 0 | 设计方案定稿 + 初始化 | 本方案、README、骨架、首次提交 | `git log --oneline` 见首次提交；目录结构与设计一致 | 你确认方案与选型，初始化完成 |
| 1 | FastAPI 骨架 + 千问直连聊天 | 可聊天的网页/接口、会话记忆 | 网页发消息、看日志 | 多轮对话能记住上下文 |
| 2 | MySQL/Milvus 接入 + 单 Agent 工具调用 | 查订单、查物流、知识问答能力 | 现场演示 + 完整工具日志 | 三类问题都能正确回答 |
| 3 | LangGraph 多智能体 | 路由 + 专家 Agent + 状态 + 完整轨迹日志 | 不同意图消息各演示一次 | 路由正确、工具参数正确、有日志 |
| 4 | 转人工 | 三种触发场景 + 上下文打包 | 按三种场景逐一演示 | 人工侧能拿到完整上下文 |
| 5 | 评测体系 | 评测集 + 跑分脚本 | 运行脚本出报告 | 报告含完成率/轨迹正确率/耗时/成本 |
| 6 | 优化迭代 | 前后对比表 | 逐点修改重跑评测 | 指标变好才保留，否则回滚 |
| 7 | 部署收尾 | Compose 部署 + 验证清单 + 演示脚本 + 简历描述 | 按清单逐步验证 | 服务可一键启动并演示 |

## 10. 协作与教学约定

- 每阶段开工前先讲：这步做什么、为什么、替代方案；你确认后再动手。
- 每实现一个可运行能力：逐块讲解代码 → 造 1~2 条真实用户消息演示 → 贴完整轨迹
  （用户说了什么 → 模型判断走哪个分支 → 调了哪个工具、传了什么参数 → 返回什么 → 最终怎么回答）。
- Agent 行为不确定时，演示必须打印完整工具调用日志。
- 每阶段末：交付物清单 + 验证方式 + 通过条件、知识点清单、3 道题（先不给答案）、一个改造小任务。
- 每阶段完成做一次 git 提交，信息格式：
  `feat(阶段N): 摘要`（功能）或 `docs(阶段N): 摘要`（文档）。

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| 大模型调用不稳定/花钱 | 用 qwen-plus，评测限量；必要时临时降级 qwen-turbo |
| 路由判断错误 | 阶段 5 评测统计意图准确率，阶段 6 针对性优化 |
| 工具失败（如 MySQL 连不上） | 工具返回结构化错误 → 如实告知用户 + 转人工兜底 |
| Agent 死循环 | LangGraph 步数上限条件边 + attempts 计数，超限转人工（阶段 3 细讲） |
| Milvus/MySQL 环境重 | docker-compose 一键启动，README 写清步骤 |
